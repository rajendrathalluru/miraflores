## Deliberate boundaries / remaining release work

1. **Shared hosting and real identity are not configured.** Local fictional personas demonstrate server policies, not proof of real staff identity or tenant membership. Configure a trusted session/authentication layer, membership-scoped Postgres policies/RLS, durable infrastructure and operational recovery before a shared deployment. The Supabase session pooler has passed connection, seeded packet read, JSON write/read and transaction rollback checks in a private `miraflores` schema.
2. **Filing, signatures, payments and messaging are simulations.** No external submission, legal signature, payment or email occurs. An identifier discrepancy can be concluded and documented; a production encrypted correction/filing-identity integration is not claimed.
3. **No OCR or tax engine.** Compatible pipeline JSON imports are dynamic. Ordinary PDFs/files are linked evidence, not a new extraction pipeline. Overlays are reviewed inputs and first-order tax-effect estimates; downstream engine results are intentionally preserved. What-if scenarios are supplied alternatives and cannot be composed into a newly computed return.
4. **Professional and product acceptance remains open.** The app exposes full supplied records, but automated checks do not independently establish every tax treatment in the design's example list. The applicant must still observe an experienced CPA and a new hire, choose a real hosted app URL, and supply their own walkthrough video.
5. **Operations require a deployment plan.** Embedded Postgres is single-process storage. Coordinated backups/restores, encryption/retention, Supabase credentials, least-privilege grants and hosted multi-session behavior are not certified by localhost tests. No production-readiness or exhaustive 105-pass claim is made.
6. **Timeline scope is explicit.** Replay constrains engine/document availability and disables live writes. It does not reconstruct every professional review mutation at every historical instant. Next-year export is a handoff with history; it does not invent a newly computed future-year return.

## Implementation choices relative to the design input

The six-destination shell, contextual inspector, dynamic packet/version model, immutable baseline, relational mutation layer, independent checks and content-bound approvals follow the design's core direction. Next.js 16 was used in place of its Next.js 15 example. A server-owned Postgres projection with React context replaces a client-only Zustand baseline store, keeping persistence and permissions authoritative on the server. Custom CSS/components and native dialogs replace the suggested Tailwind/shadcn implementation, giving direct control over the typography and compact financial interface without an additional component framework. Embedded Postgres makes the prototype runnable without Supabase credentials; the remote adapter uses the same SQL. These are implementation choices, not claims that those alternative tools were used.
