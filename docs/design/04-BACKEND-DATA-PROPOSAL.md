Reviewed October 24, 2026. The full three-page PDF, not a generic tax-product roadmap, is the scope authority. I read its complete extraction, the shared case-study brain and the first three proposals. I inspected the current domain/workflow reducers, contracts, repository, SQL migrations, database and private-file adapters, packet resolver, server boundary, attachment/identifier/examination routes and artifact builder. This round did not rerun the acceptance suites or start an app. The only fresh execution was a read-only runtime metadata query against an in-memory SQLite database.

## Recommendation

Keep the existing TypeScript modular monolith. Put its strongest asset—a reviewed, attributable, revision-controlled record—behind a clearer query and command boundary. Improve consistency, access policy and durable hosted operation before introducing more services. This preserves every PDF feature without replacing the upstream extraction/computation that the case study explicitly supplies.

Next.js/React/TypeScript with SQLite on one durable host is a credible assignment architecture, conditional on a supported patched runtime and a tested backup/restore procedure. PostgreSQL with private object storage is the right alternative if the selected host is ephemeral, uses several app instances or cannot keep a protected local volume. The choice is driven by hosting behavior, not by SQLite being intrinsically unfit for several human reviewers. PostgreSQL does not resolve stale financial decisions by itself.

The current Node executable reports **v22.15.0 with bundled SQLite 3.49.1**. The official SQLite WAL documentation now identifies a rare concurrent-connection WAL-reset defect fixed in 3.51.3 and later, with specified backports. This is not evidence of corruption here; the present process uses a singleton connection. It means a proposed hosted/multiprocess WAL configuration must verify the actual bundled SQLite fix rather than rely on `node >=22.13.0` as its operational guarantee. No upgrade was performed in this review. [SQLite WAL, section 11](https://sqlite.org/wal.html)

## Proposed read and write contracts

Use one `ReviewContext` projection constructed from one loaded review state. Its consistency token is:

```text
engagement/packetDigest + engineVersion + workspaceRevision
+ contentRevision + reviewCycle + frozenParentId/contentHash (when applicable)
+ read-only replay mode/time (when applicable)
```

The response includes stable item/document/page/field IDs, masked source observation, extraction reading/confidence, supplied computation/rule/dependencies, independent checks, active and reversed overlays, judgment/evidence, approval scopes, blockers, changed-since information and permitted actions. Each displayed value carries its provenance kind. Public DTOs must not import the raw packet module. A separate explicit logged endpoint performs sensitive reveal.

`workspaceRevision` orders every mutation; `contentRevision` identifies the material content that approvals/signatures cover. They serve different purposes. Current nonmaterial actions, including seen markers and time entries, still advance the global workspace revision. Consequently a harmless activity update can reject another person's save. Preserve the safe global CAS first; show whether the selected item's facts changed. Move per-viewer seen/notification state outside the financial aggregate only after defining its transaction and read semantics. Do not silently weaken content checks merely to reduce conflicts.

Replace the loose generic action/payload contract gradually with a discriminated runtime-validated command union: adjustment, verification, reconciliation, judgment, document disposition, question answer, approval, lifecycle, standards and protected correction. Share validated domain types with the query model; keep transport and persistence adapters thin. Zod is already installed. The current top-level route schema is strict, but its workflow payload is a record of unknown values and validation remains mostly manual inside the switch.

A proposed command request carries `expectedRevision`, an actor-bound `requestId`, target refs and validated payload. Its transaction must commit the next review state, audit, affected sign-off invalidation and related SQL metadata together. A retry with the same request ID/body returns its original result; reuse with different input fails. This handles the ambiguous case where a commit succeeds but the response is lost. Idempotency is proposed, not present in the inspected repository.

A proposed `409` returns current revision, changed refs and a safe change summary. Preserve the user's rationale in memory, reload the comparison and ask for deliberate resubmission when reviewed facts changed. Do not automatically replay a financial command. Polling can supply adequate visible freshness at this assignment's scale; show last refresh and stale state. No need to add WebSockets before a two-session task demonstrates a material latency problem.

The final frontend reply resolves an important draft distinction: ordinary non-sensitive rationale stays scoped to access session, persona, engagement/packet, engine version, item, cycle and captured content revision. Poll refresh must not reset it. Context changes require an explicit Stay/Discard decision or an actually implemented protected draft-save operation. Identifier plaintext is stricter: clear on hide, role/session change, timeout, hidden-page transition, dismissal or conflict; never restore it from a normal draft store. A refreshed context is not proof of saving, and a lost response is an uncertain commit until its request identity is reconciled. Historical replay is read-only and cannot backdate new decisions. These are proposed contracts, not assertions of current behavior.

## Persistence choice and credible alternatives

**Retain one JSON review aggregate for the case.** Its principal benefit is a small, coherent transaction boundary: state, embedded audit, approvals and frozen snapshots cannot diverge through half-written rows. Existing SQL tables handle attachments, encrypted corrections, access logs and agent runs separately. Add an explicit review-state schema version and validate/migrate saved JSON on load. Do not normalize 74 immutable document records or every supplied engine line merely because a relational database is available; in-memory indexed projections are sufficient for this packet.

Its cost is aggregate-wide conflicts, full serialization on each activity and increasingly loose query/type contracts. The audit is application-owned JSON, not an independently immutable audit store. Before larger workloads, separate actor-local activity and introduce transactionally appended audit events plus rebuildable projections. Keep material review writes under a single revision until finer approval scopes and conflict rules are actually specified.

**Credible alternative: normalized PostgreSQL review tables from the start.** Tables for engagements, packet imports, decisions, verifications, messages, approvals, filing snapshots, attachments and append-only audit enable relational constraints, scoped queries and independent indexing. They also multiply migrations and multirow invariants. For this assignment it adds migration work without proving a better CPA experience. If chosen for host compatibility, retain the reducer and implement a genuine PostgreSQL repository: SQLite `INSERT OR IGNORE`, migration syntax, driver result shape, transaction isolation and retries are not portable merely because the wrapper methods have similar names. Retain conditional revision UPDATE or row locking within the transaction. [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html)

SQLite WAL allows concurrent readers and a writer on the same host; it still has one writer at a time and is unsuitable for a shared WAL file on a network filesystem. Short human-review transactions can fit this model. Do not hold a transaction across AI calls, file I/O or HTML generation. Use PostgreSQL when separate server instances need centralized concurrent storage. [SQLite WAL](https://sqlite.org/wal.html), [appropriate uses](https://sqlite.org/whentouse.html)

No current requirement justifies Redis, a vector database, Kafka, a graph database or independent agent services. The source graph is a domain/read-model concern with roughly 3,000 values. Optional AI can search/explain that graph read-only with citations; deterministic independent arithmetic and humans remain responsible for decisions.

## Private evidence, export and recovery

The assurance reviewer found a specific export race; I independently confirmed it by reading `app/api/exam-package/route.ts`. It first captures a workspace, then separately queries **all** attachment/correction rows and reads bytes. A new attachment committed between these reads can enter the artifact without appearing in the stated workspace revision; its missing expected hash currently does not fail. New encrypted corrections can likewise be included outside the selected review state. Current serial export tests do not prove snapshot consistency under concurrent uploads.

The proposed export manifest must select exact attachment and correction IDs from the chosen review/frozen state. Capture state plus corresponding immutable metadata in a short database read snapshot, then read immutable blobs outside the transaction, require every included hash, reject absent/unexpected references and build the artifact against that captured manifest. If snapshot-consistent metadata cannot be obtained, fail or retry explicitly. It is acceptable for access logs to be appended separately if the artifact states they are export-time records rather than signed content. Preserve historical corrections as evidence without substituting newer ones into a frozen record.

Stage uploads with a lifecycle marker/creation time. Register metadata only after bytes and digest are available; make final keys immutable. A small reconciliation job can remove old unreferenced staging objects after a grace period. It must never delete referenced originals or treat a pending write as an orphan. A full distributed transaction between SQL and an object store is unnecessary; explicit state and recovery are sufficient.

Back up and restore **review database, private originals and identifier key** as one recoverable record. Protect key backup separately from ciphertext while keeping recovery coordination documented. A restored SQL file without its corresponding key cannot decrypt saved corrections. A live WAL database also needs a coherent backup method rather than copying only its main file. SQLite provides online backup and `VACUUM INTO`; choose and exercise one, then restore into a clean directory and verify expected revisions, attachment hashes, decryption and offline artifact creation. This review did not exercise restore. [SQLite backup API](https://www.sqlite.org/backup.html)

For a shared host, use an access session separate from the selectable case persona. Maintain the role switcher required by the PDF, explicitly labeled as fictional demonstration roles. Bind access session, workspace membership and selected persona on the server; no request may choose an arbitrary owner. Decide whether the hosted demo is one shared evaluator engagement or isolated evaluator copies—actual collaboration needs the same shared engagement and separate sessions.

Current bootstrap sends the **entire masked Workspace** to every persona. Masking identifiers does not establish permission to read internal staff notes/audit. Define role-specific DTO visibility and test direct API requests, including guessed IDs, original downloads, correction reveal and examiner exports. A controlled evaluator sandbox can permit role exploration, but cannot honestly be presented as genuine client least privilege. Authorize every resource request; use explicit access policy instead of hidden buttons. [OWASP authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

The local owner-only key is a useful prototype control, not a hosted key-management proof. Use a protected secret/key mechanism supported by the chosen host and verify recovery. Avoid putting plaintext corrections in logs, analytics, browser storage or AI prompts. Do not claim the current regex/source masking handles every arbitrary identifier a new user might type. [OWASP cryptographic storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)
